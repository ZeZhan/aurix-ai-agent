# AURIX MCP Server

<p align="right"><b>English</b> | <a href="./README.zh-CN.md">简体中文</a></p>

Provides project creation, builds, flashing, example imports, and documentation
search for the AURIX AI extension, directly in Copilot Chat.

## Features

| Tool | Purpose |
|------|---------|
| `ads_create_project` | Create an AURIX project |
| `build_run` | Build a project |
| `flash_program` | Flash firmware |
| `flash_list_devices` | List connected kits with board hardware version (read-only) |
| `illd_provision` | Add the required iLLD sources |
| `project_scan` | Inspect project structure, iLLD version, and available board pin labels |
| `examples_search` | Find AURIX examples |
| `examples_import` | Import an example into the workspace |
| `examples_read_source` | View example source code |
| `documentation_search` | Search AURIX documentation with source references |
| `documentation_read` | Continue reading a cited chip-documentation chunk |

## Usage

1. Install the [AURIX AI extension](../aurix-ai-agent-extension/README.md).
2. Open your project, then select a board and set the AURIX IDE path in the Configurator.
3. Enable the AURIX MCP tools in Copilot Chat's Agent mode and describe your task.

For example:

- "Find an LED blink example for the TC375 Lite."
- "Build the current project."
- "Which iLLD version does this project use?"

The extension starts the server automatically; no manual Python installation or
runtime setup is needed. For board pin queries, provide the exact board model
and hardware revision, and check the sources and applicability of the results.

## iLLD version and source

`ads_create_project`, `examples_import` and `build_run` report the iLLD version
declared in the project headers. `ads_create_project` also reports where it
came from (for example `TC37A.zip from C:\Infineon\AURIX-Configuration-Studio-1.0.24`,
or the project's existing `Libraries/` when they were kept), and
`examples_import` says whether the example bundled its own iLLD. Official
examples often bundle an older iLLD than the IDE. The template cache in
`~/.aurix-agent/device_projects` is reused only when it was built from the iLLD
archive of the currently selected IDE; selecting another IDE regenerates it.

## Build cache

Projects generated by `ads_create_project` compile the same iLLD and
configuration sources. `build_run` compiles them once per distinct input in
`~/.aurix-agent/build_cache/<key>` and copies the objects into a project whose
`build/` has no library objects yet; only the application files are then
compiled. On a TC375 project the first build after a cache entry exists took
about 17 s instead of about 3 minutes, with a byte-identical HEX file.

- The key is a content hash of the compiler executable, the Makefile's compile
  settings, every iLLD/configuration file, and any project header that could
  shadow an iLLD header. A new extension version, IDE, compiler, flag or edited
  `Ifx_Cfg.h` selects a new entry; an old entry can never match.
- Project headers outside the iLLD that library objects include are recorded
  with content hashes; if they differ, the cache is not used.
- Entries are built in place under a lock and only used once complete; the four
  most recently used entries are kept. Debug information points into the entry,
  so stepping into iLLD sources keeps working.
- Any problem falls back to a normal full build. Set `AURIX_BUILD_CACHE=0` to
  disable the cache. Makefiles generated before the cache (without the
  `illd-objs` target) and custom build commands are not affected.

## Documentation evidence

`documentation_search` returns one focused excerpt per hit: 3,000 characters
per primary hit and 2,000 per follow-up hit, taken from the hit or an adjacent
page in the same section, positioned on the window that contains the most
distinct question terms. `topK` defaults to 3; text excerpts are capped at 5,
while reviewed board LED/button facts (one line each) may return up to 10. Each
excerpt names its document, physical PDF page and, when cut, the `chunkId` for
`documentation_read`. Structured content then carries only citation metadata
(chunk IDs, document, source, pages, applicability and board flags), not the
text a second time. On the TC375 evaluation captures this reduced a typical
response from about 53,000 to about 15,000 characters. A 1,400/900-character
window was tried first and cut key facts in 4 of 20 blind-answer questions.

The full-evidence mode (`detail: "full"`) is evaluation-only: it is accepted by
the Python tool function (`documentation_search._run`, used by tests and
the evaluation runner) but not exposed in the MCP tool schema. In the first
end-to-end agent run the agent chose it in 3 of 5 calls together with
`topK` 8–10, producing 24–129 KB responses. Full mode returns the short preview
and primary citation plus `evidence` segments containing stored source text with
their own citations. Expansion is bounded to 6,000 characters per chunk and
36,000 total text characters per response, with up to two neighboring chunks per
hit in the same section, source and document version on the same/adjacent
physical pages. These budgets exclude previews and citation metadata. At large
`topK`, the per-hit budget is shared so every primary hit gets evidence.

To read beyond an excerpt, call `documentation_read` with the `chunkId` shown,
an optional `offset` (from the excerpt pointer or `nextOffset`), and the same
`device`/`family`/`indexPath`. It returns up to `maxChars` characters (default
8,000, maximum 16,000), once, in the text content; continue until `nextOffset`
is null. Unknown chunks, invalid offsets and device mismatches are errors. Board
facts still require `documentation_search` and its board/hardware/BPL checks.

The generic search returns `evidenceStatus: not_assessed` for hits:
`abstained: false` means retrieval found candidates, **not** that an answer is
complete. Check units, table headings, operating conditions, document revision
and applicable errata. Stored text may have lost PDF layout; expansion cannot
recover missing extraction data or automatically follow cross-section footnotes.
Compound questions may return partial evidence; search separately for missing
claims rather than assuming every clause is supported.

Automatic follow-up retrieval: for questions with at least 7 search terms whose
primary search found something, the tool derives up to 3 keyword queries, one
per clause (device + up to two module acronyms + up to five key terms; clauses
reduced to fewer than two key terms are skipped). It appends at most 3 new hits
after the primary `topK`, marked `retrievalPass: "follow_up"` with
`followUpQuery`, each with one 3,000-character evidence segment centred on the
first matching term. Primary results and their evidence budget are unchanged.
Questions whose primary search abstains get no follow-ups. When a query names a
board, follow-ups search that board's manual text first and chip follow-ups only
fill the remaining slots. The response also lists `followUpQueries` and, when
question identifiers or technical compounds (for example `MAC-PHY`,
`24500-hour`) appear in none of the returned text, `uncoveredTerms`.

Retrieval reranks exact and fallback matches together, demotes contents pages,
deduplicates equivalent chunks, reserves candidates from the requested device's
documents, and favors numeric resource statements or datasheet limits when
appropriate. Explicitly other-device section headings are excluded. This is
not silicon-stepping certification; generic hits remain
`applicability: requires_verification`. Explicit `device` hints now also scope
queries that do not name a device, and conflicting device hints are errors.

Board questions: reviewed LED/button facts (pin, active level) are checked
against the project BPL. Board user's manual text
is also indexed per board and hardware revision (currently the TC375 lite Kit
V2). It is returned when a query names the board, ahead of chip results and
capped at half of `topK`, or when the reviewed-fact path has no answer. With a
known, matching board revision it is usable for code generation without asking
the user (`usageRestriction: cite_board_manual_page`; cite the page in a code
comment); otherwise it is `board_hardware_version_required`. Schematics and
pin-header figures are not indexed. See
[board data](src/aurix_mcp_server/data/board_manuals/README.md).

Board hardware revision: when no `hardwareVersion` is passed (and the query or
project BPL does not state one), `documentation_search` runs
`AURIXFlasher -detect all` (about 1 s, cached for 30 s) and uses the revision of
the single connected kit that matches the board, for example
`AURIX LITE KIT V2.0 (TC375)` → `2.0`, which matches manual revision `2`. The
result carries `hardwareVersionDetected` and the text says so, so agents need
not ask the user. Detection runs only when the host sets
`AURIX_DEVICE_DETECTION=1` (the VS Code extension does); with no matching kit
connected the revision stays unknown and the agent should ask.
`flash_list_devices` lists all connected kits on demand. Detection needs
AURIXFlasher 3.1 or newer (older versions do not report board hardware); it
tries the configured studio's flasher first, then every installed one, newest
first.

These source changes must be included in the extension's bundled server and
the MCP server restarted before an installed extension can expose the new tool.
After installing an update, reload the VS Code window or restart the AURIX MCP
server: a running server keeps the old Python code in memory while reading the
newly installed data files.

## Documentation evaluation

A TC375 evaluation, kept outside the repository, provides two frozen 20-question
batches (40 English questions), five historical Chinese query pairs, captured
live retrieval results, and a repeatable source-validation/citation-scoring
runner. An English-only second round also reviews
returned-excerpt sufficiency and records separate diagnostic probes.
Page-coverage metrics are not claims of generated-answer accuracy.
